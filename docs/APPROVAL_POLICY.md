# 사용자 승인 · 수정 제한 · 작업 변경 정책 (v1)

## 기본 규칙
- 신규 **루트 작업당 FAIL 후 자동 수정 최대 3회**. 3회 수정 후에도 FAIL이면 해당 루트만 BLOCKED → GPT PM이 원인/대안/필요 횟수를 사용자와 협의 → 명시 승인 후 재개. 다른 독립 루트는 계속 운영.
- 교정 횟수는 Issue 번호나 PR 개수가 아닌 **검증된 실제 root별 수정 실행**으로 집계한다. 단순 ACK, start-only 세션, read-only 분석, PR 미생성은 이미 실행된 코드 수정과 구분한다.
- 새로운 Issue/branch/PR/루트 재라벨, 'feature' 표기, dedupe 수정으로 한도를 회피하지 않는다.
- 승인 정책의 변경은 대상 root, 이전 cap, 새로운 cap/예외 범위, 승인자, 시점, 근거 URL을 유지하며 과거 승인과 누적 수행 기록을 삭제·초기화하지 않는다.
- 기존 n의 기록 전·후 재평가, 이전 PR 재생, 수정/증거 모순을 일관되게 판정한다.

## 예외: 진행 중인 root #146
사용자는 2026-11-18 대화에서 root #146에 대하여 **정상 작동 및 전체 E2E 검증까지 승인된 범위의 수정·독립 재검수 반복**을 허용했다. 이는 다른 루트의 기본 3회 제한을 변경하지 않으며, 한도 카운터 초기화·새 root 우회·main 변경·운영 배포·유료 API/보안 완화 권한을 주지 않는다.
정확한 최신 회차와 코드상 인식되는 상한은 GitHub 승인 이력, 실행 증거, 운영 정책을 별도로 대조한다. **이 문서의 예외 문구만으로 무제한 또는 코드에 존재하지 않는 cap을 자동 발행하지 않는다**. 정책 파서와 실제 승인 사이에 불일치가 있으면 운영 BLOCKED와 PM 보고.

## 별도 명시 승인이 필요한 변경
- main 병합 또는 default-branch 워크플로 파일 활성화, 필수 체크/브랜치 ruleset 변경
- production 배포, 유료 모델 API 사용, 비밀/토큰 및 권한 확대, 보안 게이트 완화
- 기본 3회 제한 초과, 원래 요구/예산/인수 범위의 실질적 확대
- 사고 위험이 있거나 실제 GitHub 권한/증거 확인을 할 수 없는 처리

## 요구 변경
언제든 사용자 → PM에게 기능 추가·수정·취소를 요청할 수 있다. PM은 기존 결함 수정인지 신규 기능인지 분류하고 근거를 남기며 영향받는 PR·CI·검수 범위를 다시 계산한다. **신규 요구사항은 과거 FAIL 기록을 지우지 않는다**.

## 완료 기준
모든 필수 코드·보안·CI·실제 E2E 근거가 있어야 `awaiting_user_approval`. 그전에는 완료 알림이 아닌 진행/차단 보고. 승인 없이는 병합·배포 금지.
