# 단일 관리자 로그인 (Issue #87)

홈과 제어 화면은 아이디·비밀번호로 로그인한다. 회원가입, 이메일 인증, 소셜 로그인은 없다.
기본 계정/비밀번호 및 자동 생성 계정은 없다. 설정이 없거나 해시가 잘못되면 로그인은 503으로 닫힌다.
아이디·비밀번호·관리자 토큰·해시는 응답이나 브라우저 저장소에 저장하지 않는다.

## 최초 설정 (소유자가 직접 수행)

1. 고유한 관리자 아이디와 긴 무작위 비밀번호(최소 12바이트)를 정해 비밀번호 관리자에 저장한다.
2. 신뢰하는 로컬 터미널의 저장소 루트에서 아래 Bash 명령을 실행한다. 비밀번호는 화면이나 명령행 인자로 노출되지 않는다.
   `set -x` 등 셸 추적은 꺼둔다. `echo`는 줄바꿈을 추가하므로 사용하지 않는다.

   ```bash
   read -r -s -p '새 관리자 비밀번호: ' admin_password
   printf '\n' >&2
   printf '%s' "$admin_password" | node scripts/hash-admin-password.mjs
   unset admin_password
   ```

3. 서버 비밀 설정에 `ADMIN_USERNAME`과 출력된 `ADMIN_PASSWORD_HASH`를 설정한다. **평문 비밀번호는 설정하지 않는다.**
   해시 형식은 `scrypt$131072$8$1$<16바이트 salt의 hex>$<64바이트 파생 키의 hex>`다. 비용 파라미터는 고정이며
   비교 시 `timingSafeEqual`을 쓴다. 다른/약한 형식은 거부한다. 해시도 공개하거나 커밋하지 않는다.
   로컬 개발은 gitignore된 `.env.local`을 사용한다. Next.js의 `$` 변수 확장을 피하도록 해시 내부의
   **모든 `$`를 `\$`로 이스케이프**한다. 따옴표만으로는 `$` 확장을 막지 못한다.
   호스팅 환경의 비밀 입력란에는 원본 해시를 넣는다(이스케이프/따옴표 없이).
4. 기존 `CONTROL_ADMIN_TOKEN`은 서버 내부에 유지한다(16자 이상). 새 설치라면 소유자가 안전한 무작위 값을 생성해
   서버 비밀에만 설정한다. 아이디·비밀번호와 별개이며 사용자 화면에 표시하거나 입력받지 않는다.
   어떤 값도 `NEXT_PUBLIC_*` 환경변수에 넣지 않는다.
5. 개발 서버를 재시작하고 홈에서 로그인한다. 최초 설정/변경은 배포·운영 환경변수 수정 권한을 가진 소유자의 작업이다.
   이 PR은 운영 설정을 수정하거나 배포하지 않는다.

## 세션·로그아웃·폐기

- 프로덕션 쿠키: `__Host-orch_session; Path=/; HttpOnly; Secure; SameSite=Strict`, Domain 없음. 운영은 HTTPS 필수다.
  HTTP 로컬 개발에서만 `orch_session` 이름을 쓰고 Secure를 생략한다.
- **로그인 상태 유지**는 기본 미선택이다. 선택하면 `Max-Age=2592000`과 절대 만료 30일(슬라이딩 없음).
  미선택이면 `Max-Age`/`Expires` 없는 브라우저 세션 쿠키이며, 서버에서도 12시간 후 만료한다.
  브라우저의 세션 복원 기능은 세션 쿠키를 복원할 수 있으므로 공용 기기에서는 명시적으로 로그아웃한다.
- 쿠키에는 난수 세션 ID·역할·발급/만료 시각과 HMAC만 들어간다. 서명 키는 서버의 역할별 API 토큰에서 파생하며
  관리자 아이디·비밀번호 해시·`CONTROL_SESSION_EPOCH`에도 묶인다. 계정/해시/토큰/EPOCH 변경 시 기존 세션은 무효다.
  이번 키 형식 변경은 기존 브라우저 쿠키를 무효화하므로 한 번 재로그인해야 한다.
- 로그아웃은 CSRF 검증 후 쿠키를 `Max-Age=0`으로 삭제한다. 실패하면 UI가 로그아웃 완료로 표시하지 않는다.
  무상태 세션이므로 개별 서버 폐기 목록은 없다. 쿠키 탈취가 의심되면 `CONTROL_SESSION_EPOCH`를 변경해 전체 폐기한다.
- 세션 만료(401) 시 클라이언트는 로그인 화면으로 돌아가고 로그인/로그아웃 시 기존 전역 새로고침 구독을 갱신한다.
  시간 표시는 기존 KST 포매터를 사용한다. 내비게이션/디자인 개편은 없다.

## CSRF·로그인 시도 제한

- 로그인은 정확한 동일 출처 Origin(운영은 HTTPS) 또는 `Sec-Fetch-Site: same-origin` 증거를 요구한다.
  `cross-site`/`same-site` 헤더 및 임의 `x-forwarded-host`로 출처 검사를 우회할 수 없다.
- 쿠키 기반 변경 요청과 로그인된 세션의 로그아웃은 동일 출처 증거와 세션별 `x-csrf-token`이 모두 필요하다.
  `GET /api/session`으로 받은 CSRF 값은 메모리에만 보관한다.
- `/api/reconcile` GET은 명시적 `x-admin-token` 관리자 토큰 또는 `Authorization: Bearer <CRON_SECRET>`만 허용한다.
  **쿠키만으로 GET reconciliation은 실행하지 않는다.** 브라우저는 POST + CSRF로 호출한다.
- 로그인 요청은 단일 관리자 계정 전체에서 프로세스당 **15분에 5회**로 제한하며 성공/실패 모두 횟수에 포함한다.
  비밀번호 해싱 전에 동기적으로 예약하므로 동시 요청도 제한된다. 초과 시 429 + `Retry-After`(초)를 반환한다.
  사용자가 보낸 IP·아이디를 제한 키로 사용하지 않아 헤더/아이디 교체로 한 프로세스의 제한을 우회할 수 없다.
  이 예산은 토큰→세션 교환에도 적용되지만 기존 API의 헤더 토큰 인증에는 적용하지 않는다.
- **제한 범위:** 카운터는 프로세스 메모리다. 재시작/서버리스 콜드 스타트 시 초기화되며 여러 인스턴스에서 공유되지 않는다.
  다중 인스턴스 운영의 전역 제한이 필요하면 소유자가 WAF/공유 저장소 기반 로그인 제한을 별도로 구성해야 한다.
  이 구현이 분산 전역 제한을 제공한다고 주장하지 않는다.

## 기존 API·데모 호환성

`x-admin-token` 관리자/읽기 토큰, 크론 Bearer, 에이전트 HMAC·세션 콜백 계약은 유지한다.
기존 스크립트의 `{token}` 세션 교환도 호환하되 브라우저 UI에는 노출하지 않는다.
잘못된 명시적 토큰은 유효한 쿠키로 폴백하지 않는다. 헤더 토큰은 ambient credential이 아니므로 CSRF 불필요다.

격리 데모에는 데모 전용 관리자 아이디·해시·서버 내부 토큰만 사용한다. 실제 운영 자원/비밀은 복사하지 않는다.
`GET /api/collaboration`을 포함한 모든 데이터 읽기는 합성 픽스처로 응답한다. 시나리오·KST·전역 새로고침은 유지한다.
데이터 변경(크론 GET 포함)은 403이며 운영/실제 자원 감지 시 503으로 fail-closed다.
Node 런타임에서도 게이트를 재검증해 middleware 외의 진입 경로에서 실제 의존성에 접근하지 않게 한다.
로그인·로그아웃과 비민감 데모 시나리오 쿠키 변경은 기존 예외이며 외부 서비스/DB를 호출하지 않는다.

검증: `npm ci`, `npm run typecheck`, `npm test`, `npm run build`.
빌드 후 `node --test scripts/login-smoke.test.mjs`는 임시 디렉터리·자체 서버·테스트 전용 인증으로 실제 HTTP 동작을 검증한다.
운영 서버/자격증명 또는 실제 GitHub/에이전트를 호출하지 않는다.
