# 오케스트레이터 운영 매뉴얼

코드를 직접 읽지 않아도 운영할 수 있도록 쓴 사용 설명서입니다. 저장소마다 같은 엔진(`scripts/orch/` + 엔진 워크플로, 설치 목록은 [NEW_PROJECT.md](NEW_PROJECT.md)의 1장 2번 '엔진 설치')이 설치되어 있고, 이 문서는 그 공통 사용법입니다.

새 프로젝트(저장소)를 올릴 때는 먼저 [새 프로젝트 시작 절차](NEW_PROJECT.md)를 순서대로 따릅니다.

## 1. 한눈에 보기

| 역할 | 누가 | 하는 일 |
| --- | --- | --- |
| PM | Claude | 요구를 듣고 계획 Issue를 씀, 멈추면 Codex PM 이 바로 진단, 풀 수 있으면 재개(자동 모드·Codex 켜짐일 때), 판단이 필요할 때만 알림 |
| 구현 | Claude Sonnet / Opus | 스텝 하나씩 구현 (모델은 스텝마다 자동 선택, 7장) |
| 검수 | Codex (기본) → 안 되면 Claude Opus | 스텝 PR을 작성자와 분리된 세션에서 검수 |
| 자동 검사 | GitHub Actions CI | `npm test` 등 |
| 승인 | **사용자** | 시작(`orch:go`), 위험한 변경의 최종 머지 — 자동 모드(`ORCH_AUTO`)를 켜면 둘 다 AI에게 맡김 |

흐름: 계획 Issue → `orch:go` → 스텝마다 [구현 → PR → 검수 + CI → 통과면 다음 스텝 / 실패면 수정, 최대 3회] → 최종 PR + 완공 보고서 → 위험 낮으면 자동 머지, 높으면 사용자 승인(자동 모드면 위험과 상관없이 CI 통과 후 자동 반영).

PC를 꺼도 GitHub에서 돌아갑니다. 별도 유료 API는 쓰지 않습니다 (Claude 구독 토큰, Codex 연결).

## 2. 새 작업 시작하기

1. Claude(PM)에게 하고 싶은 일을 말합니다. PM이 계획 Issue를 만듭니다 (템플릿 "Orchestrator 계획").
2. Issue를 보고 괜찮으면 **`orch:go` 라벨**을 붙입니다. 저장소 소유자가 쓴 Issue에 소유자가 붙인 라벨만 동작합니다.
   - **상황판 PM 브리핑 탭에서 승인 가능 (ORCH_GITHUB_TOKEN 에 Issues 쓰기 권한 필요)**: '승인 대기 계획'에 목표·스텝 수·계획 감사 결과가 보이고, 관리자 로그인에서 '승인' → '정말 시작할까요? 승인'을 차례로 누르면 앱이 소유자 토큰으로 `orch:go`를 붙입니다. 화면을 연 뒤 계획이 바뀌었으면 승인하지 않고 새로고침하라고 알려 줍니다.

계획은 Issue 본문의 ```` ```json ```` 블록입니다.

| 항목 | 필수 | 뜻 |
| --- | --- | --- |
| `goal` | ✅ | 한 줄 목표 (최종 PR 제목이 됨) |
| `steps[]` | ✅ | 최대 10개. 각 스텝: `id`(1부터), `title`, `task`, `done_when`(기계가 확인할 수 있는 완료 기준) |
| `steps[].stop_if` | | 이런 상황이면 멈추고 사람에게 물어봄 |
| `steps[].model` | | 이 스텝만 모델 지정 (`sonnet` / `opus` / `fable`) |
| `model` | | 계획 전체 기본 모델 |
| `max_retries` | | 검수 실패 시 수정 횟수 (0~3, 기본 3) |
| `auto_merge` | | `false`면 위험이 낮아도 사람이 머지. 단 자동 모드(`ORCH_AUTO`)가 꺼져 있을 때만이고, 켜져 있으면 `false`여도 CI 통과 후 자동 반영 (아래 [자동 모드](#자동-모드-orch_auto-상황판-ai-팀-탭-스위치) 4번) |
| `try` | | 완공 보고서의 "확인 방법"에 들어갈 사용법 |
| `context` | | 기술 스택, 제약 등 |

### 계획 감사 (claudex 루프)

PM이 계획 Issue(제목 `[plan] ...`)를 쓰면 `orch:go` 전에 **Codex가 계획을 감사**합니다(`plan-review` 워크플로).

1. Issue가 열리거나 계획 JSON이 바뀔 때마다 한 라운드 감사합니다. 최대 3라운드이고, 본문이 그대로면 다시 감사하지 않습니다.
2. 확인하는 것: 실제 코드와 맞는지, 스텝 분할·순서, `done_when`이 기계로 확인 가능한지, 빠진 테스트·문서, 보안·회귀 위험, 모델·자동 머지 선택.
3. 결과는 Issue 댓글 "계획 감사 N/3"으로 남습니다. ✅ OK면 승인 가능, ✏️ 수정 필요면 PM이 고치고 다음 라운드가 자동으로 돕니다.
4. Codex를 쓸 수 없으면(OFF·한도·로그인 없음) Claude Opus가 `planner`·`architect` 보조 에이전트로 대신 감사합니다.
5. 사용자는 마지막 감사가 OK인 것을 보고 `orch:go`를 붙이면 됩니다. 급하면 감사를 기다리지 않고 바로 붙여도 됩니다(붙이는 순간 감사는 멈춤).

## 4. 끄고 켜기 (ON/OFF)

GitHub 저장소 **Settings → Secrets and variables → Actions → Variables** 탭에서 바꿉니다. 상황판의 스위치도 같은 값을 바꿉니다. 상황판 스위치는 **등록된 모든 프로젝트에 한 번에 적용**됩니다(저장소마다 따로 바꾸지 않음). 저장소마다 값이 다르면 AI 팀 탭에 '일부 프로젝트 값이 다름'이 뜨고, **모두 맞추기**로 상황판 저장소 값에 맞춥니다.

| 변수 | 값 | 기본(비워두면) | 꺼졌을 때 |
| --- | --- | --- | --- |
| `ORCH_SONNET` | `on` / `off` | on | Sonnet이 할 일을 Opus가 함 (Opus도 꺼지면 대기) |
| `ORCH_OPUS` | `on` / `off` | on | Opus가 할 일을 Sonnet이 함. Codex를 못 쓸 때 대체 검수자가 없어 검수 대기 |
| `ORCH_FABLE` | `on` / `off` | on | `model: "fable"` 스텝을 Opus가 함 |
| `ORCH_CODEX` | `on` / `off` | on | Codex를 기다리지 않고 Opus가 바로 검수. Codex가 남긴 결과는 무시 |
| `ORCH_PAUSED` | `on` / `off` | off | `on`이면 새 작업(구현·수정·대체 검수)을 전부 멈춤 |
| `ORCH_CODEX_DEV` | `on` / `off` | on | Claude 사용량 한도일 때 Codex가 구현·수정·PM을 대신하지 않고 한도가 풀릴 때까지 대기 (6장) |
| `ORCH_AUTO` | `on` / `off` | off | **자동 모드**(5장 아래). 꺼져 있으면 시작(`orch:go`)과 위험 변경 반영을 사람이 함 |
| `ORCH_WINDOW` | `HH:MM-HH:MM` | 항상 | 한국시간 이 시간대에만 새 작업 시작. 예: `08:00-24:00`, `22:00-06:00`(자정 넘김). 형식이 틀리면 안전하게 "닫힘"으로 처리 |

- **이미 돌고 있는 작업은 끝까지 마칩니다.** 스위치는 새로 시작하는 일만 막습니다.
- 꺼서 멈춘 작업은 Issue에 "⏸️ 대기"로 한 번 기록되고, 시간 초과로 중단되지 않습니다.
- 다시 켜면 다음 순찰(매시 7·27·47분) 때 자동으로 이어집니다. GitHub가 정기 실행을 몇 시간씩 미루거나 건너뛸 때가 있으니, 바로 이어가려면 Actions → `orchestrator` → **Run workflow**를 누르면 됩니다.
- 한계: Codex 앱이 PR을 보고 스스로 리뷰하는 것은 GitHub 밖 설정이라 막을 수 없습니다. 꺼져 있을 때는 그 결과를 판정에 쓰지 않을 뿐입니다. 완전히 막으려면 Codex 설정에서 이 저장소의 Code review를 끄세요.

## 5. 승인 — 자동 머지와 확인 필요

- 스텝 PR은 검수 + CI 통과 시 통합 브랜치(`orch/run-N`)에 자동으로 합쳐집니다. 판정한 커밋에서 바뀌었으면 합치지 않습니다.
- 최종 PR(→ `main`)은 **위험이 낮으면 CI 통과 후 자동 머지**, 아래에 해당하면 **완공 보고서와 함께 승인 요청**합니다.
  - DB 구조 변경(마이그레이션·스키마), 로그인·결제·권한·세션·토큰 관련 코드, 인증서
  - GitHub Actions·저장소 설정, 오케스트레이터 자체 변경
  - 배포·빌드 설정(`vercel.json`, `next.config` 등), 환경변수 파일
  - 새 외부 패키지·의존성 잠금 파일 변경, 변경 파일 40개 초과
- 자동 모드(`ORCH_AUTO`)가 켜져 있으면 위 위험 항목도 CI 통과 후 자동 반영합니다(아래 자동 모드 4번).
- 엔진(구현·검수 AI)은 배포하지 않습니다. 운영 배포는 별도 `deploy` 워크플로가 main 반영 10건(`ORCH_DEPLOY_EVERY`)마다 Vercel Deploy Hook을 부르거나 사용자가 수동 실행합니다(아래 운영 배포 절).

### 자동 모드 (`ORCH_AUTO`, 상황판 AI 팀 탭 스위치)

사용자가 시작·반영 승인을 AI에게 맡기는 모드입니다. 켜면 사람 없이 이렇게 돕니다.

1. 계획 감사가 **OK**면 바로 `orch:go`를 붙여 시작합니다(소유자 토큰 `BOT_PAT`).
2. **수정 필요**면 `plan-revise` 워크플로에서 PM(Claude Opus)이 지적마다 코드를 확인해 계획을 고치고, 이슈에 "🤖 PM 자동 반영" 댓글로 지적별 반영 내용을 남깁니다. 고친 본문이 다음 라운드 감사를 엽니다. 마지막 라운드 전에는 결과에 따라 갈립니다: PM이 계획을 바꾸면 다음 라운드 감사로 가고, 고칠 것이 없다고 판단해 유효한 같은 계획을 내면 재감사 없이 기존 계획으로 시작하며(수정 필요였어도), 고친 계획을 쓰지 못하면(형식 오류 등) 그 계획만 멈춥니다.
3. **마지막(3) 라운드**도 수정 필요면 PM이 남은 지적을 반영한 뒤 다시 감사하지 않고 시작합니다. 마지막 라운드에서는 고친 계획을 쓰지 못해도 원래 계획으로 시작합니다.
4. 최종 PR은 **위험 등급과 상관없이** CI 통과 후 자동 반영합니다. 완공 보고서의 '주의할 점'은 그대로 남고 완료 알림이 갑니다.
5. 사용자 승인 대기(`awaiting_merge`) 중인 run이 있을 때 자동 모드를 켜면, 다음 순찰에서 자동 반영 경로로 넘깁니다.
6. **다음 계획도 자동으로 씁니다.** run이 끝나면(또는 순찰 때 아무것도 진행 중이 아니면) `plan-next` 워크플로가 돕니다. Codex가 먼저 읽기 전용으로 지금 단계의 남은 일과 관련 코드·테스트를 정리하고, PM(Claude Opus)이 그걸 참고해 `docs/roadmap.json`·`docs/PM_HANDOFF.md` 기준으로 다음 계획 Issue를 씁니다. 이 Issue는 감사 → 자동 시작으로 이어집니다. 단계의 AI 몫이 끝나 보이면 Codex가 **단계 통합 검수**(로드맵 목표·문서·코드·테스트가 맞는지)를 하고, 빠진 게 있으면 그것부터 계획합니다. 빠진 게 없을 때만 다음 계획의 첫 스텝에서 로드맵 단계를 완료로 바꾸고 다음 단계로 넘어갑니다.
7. **사람만 할 수 있는 일**(운영 배포, 비밀값·환경변수, 외부 콘솔, 사용자 확인)은 계획에 넣지 않고, 끝났다고 가정한 채 나머지를 진행합니다. 그 일은 `orch:human` 라벨 Issue **"사람 할 일 (자동 모드)"**에 체크리스트로 쌓이고 폰으로 알립니다. 대화를 시작하면 PM이 이 목록부터 같이 봅니다.
8. 멈춤 장치: 열린 계획·진행 중 run·중단된 run이 있으면 새 계획을 쓰지 않습니다. 하루 자동 계획은 최대 8개(`ORCH_DAILY_PLANS`로 변경)입니다. "할 일 없음"으로 끝나면 main이 바뀔 때까지 다시 쓰지 않고, 작성이 실패하면 1시간 뒤 다시 시도합니다.

자동 모드에서도 바뀌지 않는 것: 엔진(구현·검수 AI)은 배포하지 않습니다. 운영 배포는 별도 `deploy` 워크플로가 main 반영 10건(`ORCH_DEPLOY_EVERY`)마다 Vercel Deploy Hook을 부르거나 사용자가 수동 실행합니다(아래 운영 배포 절). 구현 Claude는 `.github/`·`scripts/orch/`를 바꿀 수 없어 엔진 변경은 PM의 PR을 사람이 반영합니다. ON/OFF·시간대·수정 3회 제한·사용량 한도 대기는 그대로 적용됩니다.

**최종 PR이 main과 충돌할 때:** 그사이 다른 작업이 main에 반영되면 최종 PR이 충돌해 CI가 돌지 않습니다. 엔진이 이를 감지해 `final-sync` 워크플로로 main을 합칩니다. 충돌이 패치노트(`src/lib/patchnotes.ts`)뿐이면 양쪽 항목을 모두 남기고 버전 순으로 자동 정리한 뒤 CI를 다시 봅니다. 그 밖의 충돌은 "중단"으로 알리니, 충돌을 풀고 `orch:go`를 다시 붙여 주세요.

## 6. 멈췄을 때

| 하고 싶은 것 | 방법 |
| --- | --- |
| 이어가기 | 원인을 해결한 뒤 계획 Issue에 `orch:go` 라벨 |
| 취소 | `orch:cancel` 라벨 |
| 위험 변경 머지 | 최종 PR의 "주의할 점"을 읽고 Merge. 머지하거나 닫으면 엔진이 바로 run을 완료·취소 처리합니다(순찰을 기다리지 않음) |

**Claude 사용량 한도에 걸리면** 중단하지 않고 "⏸️ 대기"로 바꿉니다. 실행 기록에서 한도가 풀리는 시각을 읽어 이슈에 남기고, `wait` 워크플로가 그 시각(+1분)까지 기다렸다가 엔진을 깨워 같은 스텝을 이어 갑니다(7일 한도처럼 길면 5시간 45분씩 나눠 기다림). 풀리는 시각을 읽지 못한 실패는 지금처럼 "중단"입니다.

**Codex 개발 대체 (`ORCH_CODEX_DEV`, 기본 on, `ORCH_CODEX`도 on일 때):** 한도에 걸리면 기다리지 않고 **Codex가 같은 스텝의 구현·수정을 이어서** 합니다(`claude-work`의 `impl=codex`). 같은 지시·같은 CLAUDE.md 규칙을 따르고, PR·댓글의 구현 모델에 `codex (Claude 사용량 한도로 대체)`로 남습니다. 한도가 풀린 뒤 Codex가 만든 스텝은 **Claude(Opus)가 독립 검수**하고, 다음 스텝부터는 다시 Claude가 구현합니다. 한도 중에는 Codex가 검수도 해서 밤새 멈추지 않지만, 이렇게 **Codex가 만들고 Codex가 검수한 스텝은 '임시 통과'**입니다. 모든 스텝이 끝나면 최종 PR을 main에 반영하기 전에 **Claude(Opus)가 임시 통과 스텝을 run 전체 diff로 다시 검수**합니다(상태 'Claude 재검수 중'). 한도가 아직이면 풀리는 시각까지 기다리고, FAIL이면 run 브랜치에서 Claude가 고쳐 다시 검수합니다(최대 수정 횟수 동일). 그래서 main에는 항상 만든 AI와 다른 AI의 검수를 거친 코드만 들어갑니다. 계획 작성(`plan-next`)·감사 반영(`plan-revise`)도 Claude가 결과를 못 내면 Codex가 PM 역할을 대신합니다.

**반복 실패 원인 분석:** 같은 스텝이 검수에 2번 떨어지면, 3번째 수정 전에 Codex가 읽기 전용으로 근본 원인·꼭 바꿀 것·하지 말 것을 정리해 구현 지시 끝에 붙입니다(참고용).

자동 모드와 Codex가 켜져 있으면 중단 즉시 `pm-unblock` 워크플로에서 Codex가 PM으로 원인을 진단합니다. 자동으로 풀 수 있다고 판단하면 계획에 [PM 지시]를 붙여 재개하고(run당 3회), 풀 수 없다고 판단하거나 결정을 쓰지 못하면 Issue에 사람 판단 요청을 남깁니다. 최종 PR 문제, 3회 소진, 자동 모드나 Codex가 꺼진 경우는 사람 판단이며 Issue에 남기고 폰으로 알립니다.

## 7. 구현 모델 선택

1. 스텝의 `model` → 2. 계획의 `model` → 3. 자동
   - 자동: 스텝 제목·내용에 DB·인증·로그인·비밀번호·결제·권한·보안·배포 관련 말이 있으면 **Opus**, 아니면 **Sonnet**
2. `"fable"`은 Claude Fable(`claude-fable-5-2`)로 실행합니다. 가설·분석·모델 설계처럼 깊게 생각할 스텝에 계획이 직접 지정할 때만 쓰고 자동 선택은 하지 않습니다. Fable이 과부하면 그 실행은 Opus로 넘어가고, `ORCH_FABLE`이 off면 처음부터 Opus입니다.
3. Sonnet으로 검수에 **2번** 떨어진 스텝은 다음 수정부터 Opus로 올립니다.
4. ON/OFF 스위치가 마지막에 적용됩니다 (4장).

완공 보고서 "검사 결과" 표에 스텝별 구현 모델·**쓴 스킬과 보조 에이전트**·검수자·수정 횟수가 나옵니다. 스텝 PR 본문의 "도구 사용 (자동 기록)"에는 구현 Claude가 실제로 쓴 도구 횟수, 스킬(예: ECC `verification-loop`), 보조 에이전트(예: `build-error-resolver`), 돌린 검증 명령(typecheck/test/build)이 실행 기록에서 자동으로 뽑혀 남습니다. ECC 효과는 이 기록과 수정 횟수를 run별로 비교해서 봅니다.

스텝 PR 본문과 "수정 N회차 반영" 댓글에는 그때 쓴 **구현 모델**(예: `opus (검수 2회 실패로 상향)`)이 표시됩니다. Codex 대신 Opus가 검수할 때는 ECC 검수 에이전트(`code-reviewer`, `security-reviewer`, `typescript-reviewer`, `react-reviewer`)를 보조로 부를 수 있고, 쓴 에이전트는 검수 댓글의 "도구 사용"에 남습니다. 검수 세션은 PR이 아니라 `main`의 `.claude/`를 쓰므로 구현자가 검수 지시를 바꿀 수 없습니다.

화면(UI) 스텝에서는 구현 Claude가 디자인 스킬 **Impeccable**(`.claude/skills/impeccable`)을 따릅니다. 상황판은 Operate 모드(훑어보기·일관성·모바일 우선)이고, 기존 화면 수정은 기존 디자인을 유지하는 refinement가 기본입니다. 규칙은 CLAUDE.md "디자인 스킬" 절.

**결과 화면 테스트 (Playwright):** 모든 PR의 CI에서 `screens` 검사가 실제 빌드를 띄우고 실제 로그인으로 5개 탭(프로젝트·AI 팀·PM 브리핑·패치노트·구조)을 폰 폭 360/390/430px로 엽니다. 기대 문구가 보이는지, 가로로 넘치는지, 페이지 오류·외부 요청·GitHub 쓰기가 없는지 확인합니다. GitHub API는 가짜 서버(`scripts/screens/fixtures.mjs`)를 씁니다. 스크린샷 18장은 해당 CI 실행의 **Artifacts → screens**에서 받을 수 있습니다. 로컬에서는 `npm run build && npm run screens`. 스위치 저장을 머지 전에 확인하려면 `SCREENS_SWITCH=ok npm run screens`(모두 저장 성공 → 'n개 프로젝트에 적용', `switch-ok.png`)와 `SCREENS_SWITCH=partial npm run screens`(한 저장소 저장 실패 → '일부 실패: …', `switch-partial.png`)를 따로 실행합니다. 이 쓰기는 테스트 안의 가짜 GitHub 서버에만 가고 실제 저장소 설정은 바꾸지 않습니다.

## 9. 안전장치 (하지 않는 것)

- 소유자가 아닌 사람의 Issue·라벨로는 시작하지 않습니다.
- 구현하는 Claude는 푸시·PR·워크플로 수정 권한이 없고, `.github/`·`scripts/orch/`를 바꾸면 푸시를 거부합니다.
- 검수는 구현과 다른 세션·계정에서 하며, 정해진 계정이 쓴 판정만 믿습니다.
- 자동 모드가 꺼져 있으면 사용자 승인 없이 위험한 변경을 `main`에 넣지 않습니다(켜면 사용자가 그 승인을 맡긴 것). 엔진은 배포하지 않으며, 운영 배포는 `deploy` 워크플로가 main 반영 10건마다 합니다.
- 보안 점검 항목과 코드·테스트 근거, 사람이 확인할 운영 설정은 [보안 점검표](SECURITY_CHECKLIST.md)에 있습니다.

  - 선택 필드 `phases[].tasks`: `[{ "title": "…", "owner": "me", "status": "todo" }]` — PM이 관리하는 세부 할 일(`title` 40자까지, `owner` me=사람('나' 칩)·ai('AI' 칩), `status` done·todo). 미완료(todo)만 그 단계 묶음에 보입니다.
  - 계획 JSON 최상위의 선택 필드 `"phase": "6"`(= `phases[].id` 문자열)은 **PM이 적습니다**. 이 값이 있으면 그 단계 묶음에 들어가고, 없으면 `ref`로 연결합니다(엔진은 이 필드를 무시). 자동 완료는 `ref` 연결에만 적용되므로, `phase` 필드로만 이어진 단계는 여러 계획이 한 단계에 속할 수 있어 PM이 roadmap `status`를 done으로 바꿉니다.

- 상황판 스위치는 4장의 저장소 변수를 등록된 모든 저장소에 저장하고 저장소마다 엔진을 바로 깨웁니다(한 저장소가 실패해도 나머지는 계속, 실패한 저장소는 따로 표시). 그래서 대기 작업이 다음 순찰(매시 7·27·47분)을 기다리지 않고 이어집니다.
- 상황판이 꺼져 있거나 고장 나도 엔진은 GitHub 변수만 보고 움직입니다.
- 서버 설정(Vercel): `ORCH_REPOS`(보여줄 저장소, 쉼표 구분), `ORCH_GITHUB_TOKEN`(해당 저장소 Issues 읽기, Variables 읽기·쓰기, Actions 읽기·쓰기, **등록 저장소 Contents 읽기(docs/architecture.json)** — roadmap.json·patchnotes.json도 같은 권한). 토큰이 없으면 읽기만 됩니다.
  - `ORCH_APP_URLS`(선택): 프로젝트 카드 '화면 열기' 주소, 쉼표 구분 `owner/repo=라벨|https://주소`(라벨 생략 가능, 예: `owner/repo=가계부|https://app.example.invalid`). 공개 저장소는 운영 주소를 `roadmap.json` 대신 여기에 둡니다. `https://`만 받고, 상황판 자기 저장소 항목은 무시합니다.

  | 토큰 권한 | 용도 |
  | --- | --- |
  | Issues 읽기·쓰기 | run·계획·아이디어 읽기, 계획 승인, 아이디어 등록 |
  | Variables 읽기·쓰기 | ON/OFF 스위치 (모든 등록 저장소) |
  | Actions 읽기·쓰기 | 엔진 깨우기, 사용량 갱신 |
  | Contents 읽기 | 등록 저장소 `docs/roadmap.json`·`docs/patchnotes.json`·**`docs/architecture.json`**(구조 탭, 상황판 자기 저장소는 읽지 않음, 64KB 초과는 형식 오류) |

### 사용량은 어떻게 재나요
- `usage` 워크플로가 매시 17분에 돌아요. Claude Code를 Haiku로 한 번("OK" 한 단어) 실행하면 Claude가 돌려주는 한도 정보(5시간·7일 사용률, 리셋 시각)가 나오고, 그걸 `orch:usage` 라벨 Issue에 저장해요. 값은 **구독 계정 전체** 기준이라 직접 대화로 쓴 양도 포함돼요. 전체 일시정지 중에는 확인을 건너뛰고 마지막 값을 유지해요.
- Codex는 3시간마다 공식 `codex app-server`의 `account/rateLimits/read`로 5시간·주간 사용률과 리셋 시각을 읽어요. 이때 필요한 Codex 로그인 정보는 암호화해서(AES-256, 열쇠는 시크릿 `CODEX_AUTH_KEY`) GitHub Actions 캐시에 보관해요. 실행할 때마다 복원 → 조회 → 토큰이 바뀌었으면 다시 암호화해서 저장 → 실행 컴퓨터에서 삭제하는 순서로 돌아요. GitHub 리뷰 기록으로 본 "한도 소진" 여부도 같이 표시해요.
- **처음 한 번 (폰으로)**: ① 저장소 Settings → Secrets and variables → Actions → New secret → 이름 `CODEX_AUTH_KEY`, 값은 20자 이상 아무 문자열 ② Actions → `codex-login` → Run workflow ③ 실행 요약(또는 `orch:usage` Issue 댓글)에 나온 주소를 열고 코드를 넣어 승인.
- 로그인이 풀리면 상황판과 `orch:usage` Issue에 "폰 로그인 필요"가 뜨고, ②~③만 다시 하면 돼요. 이 로그인 정보는 사용량 조회에만 쓰여요.
- 문서화되지 않은 정보라 형식이 바뀌면 "확인 불가"로 표시돼요. 엔진 동작에는 영향이 없어요.


## 운영 배포 (10개 업데이트마다)

Vercel 자동 배포는 꺼져 있습니다(`vercel.json`). 무료 플랜의 하루 배포 한도를 보호하기 위해서입니다. 대신 `deploy` 워크플로가 main에 커밋(first-parent 기준)이 **10개** 쌓일 때마다 Vercel Deploy Hook으로 한 번 배포합니다.

- 기준점: 태그 `prod-deployed`는 배포 대기 수를 세는 기준점입니다(deploy 워크플로가 Hook 요청을 보낸 뒤 그 커밋으로 옮깁니다). 태그 위치가 실제 배포 성공을 뜻하지는 않습니다. 개수는 그 이후 main에 쌓인 커밋 수(first-parent 기준: 머지·squash 머지·직접 커밋 각각 1개, `git rev-list --count --first-parent prod-deployed..HEAD`)입니다.
- 프로젝트 카드 머리의 배포 문구: 비교 대상은 `prod-deployed...main` 고정이고, compare 404 또는 기준점 뒤 대기가 0이면 '배포 완료', 대기가 있으면 '배포 대기 N', 404 이외의 오류(403·500 등)나 읽기 실패는 '배포 대기 ?'로 표시합니다. 'N'도 위와 같은 first-parent 기준입니다. 완전성 검사는 다음과 같습니다: `total_commits`가 받은 커밋 수와 다르면(250개에서 잘린 경우 포함) '배포 대기 ?', `total_commits` 없이 커밋이 250개 이상 오면 '배포 대기 ?', 한 줄로 이어진(단일 체인) 커밋 250개가 `total_commits` 250과 함께 모두 오면 '배포 대기 250'입니다. 형식을 읽을 수 없으면 '배포 대기 ?'이고, 250개를 다 받아도 머지로 들어온 옆 가지 커밋이 섞여 있으면 first-parent 경로의 커밋만 세므로 250보다 작게 나옵니다. '배포 완료'는 카드 표시 조건일 뿐 워크플로가 방금 배포했다는 뜻은 아닙니다. 그래서 첫 배포 전 저장소도 '배포 완료'로 보일 수 있습니다. compare 404는 태그 `prod-deployed`가 없을 때(첫 배포 전), 기본 브랜치가 main이 아닌 저장소에 main 브랜치가 없을 때, 토큰 권한이 없어 GitHub가 404로 답할 때 모두 같은 응답이라 상황판은 구별하지 않고(기본 브랜치 조회 등 추가 API 호출 없음) 모두 '배포 완료'로 표시합니다(접근 거부가 403 등 404가 아닌 오류로 오면 '배포 대기 ?'). 기본 브랜치 이름이 달라도 main 브랜치가 있으면 그것만으로 404가 나지는 않습니다. 그래서 실제 배포 여부는 카드가 아니라 아래 '배포 요청 확인'(GitHub Actions의 `deploy` 실행)과 '빌드 확인'(Vercel Deployments)으로 확인합니다.
- 배포 요청 확인: 배포 요청이 나갔는지는 GitHub Actions → `deploy` 실행 기록의 'Trigger Vercel deploy hook' 단계가 성공했는지로 확인합니다.
- 기준 갱신 확인: 대기 수 기준이 갱신됐는지는 같은 실행의 'Remember deployed commit' 단계와 태그 `prod-deployed` 위치로 확인합니다. 이 단계만 실패하면 배포 요청은 이미 나갔어도 카드의 대기 수가 줄지 않습니다.
- 빌드 확인: Vercel 빌드가 성공했는지는 Vercel 대시보드 → `ai-orchestrator` → Deployments에서 확인합니다.
- 지금 바로 배포하려면 GitHub 앱 → Actions → `deploy` → **Run workflow**를 누릅니다(기본값이 강제 배포).
- 기준 개수는 저장소 변수 `ORCH_DEPLOY_EVERY`로 바꿀 수 있습니다(기본 10).
- 한 번만 설정하면 됩니다: Vercel → `ai-orchestrator` → Settings → Git → **Deploy Hooks**에서 이름 `orch`, 브랜치 `main`으로 만들고, 나온 URL을 GitHub 저장소 Settings → Secrets and variables → Actions → **New repository secret** `VERCEL_DEPLOY_HOOK`에 넣습니다.
- 배포 전 화면은 각 PR의 CI `screens` 스크린샷(Artifacts)으로 확인합니다.

## 아이디어함

생각날 때 아이디어를 적어 두면 Claude(PM)와 Codex가 의견을 내고, 종합 의견을 남깁니다. 개발 여부는 나중에 정합니다.

- 제목이 `[idea] 항목`인 Issue를 소유자가 쓰면 됩니다(상황판 입력창도 같은 Issue를 만듭니다). 본문에는 내 의견을 적습니다.
- `idea-review` 워크플로가 Codex 의견 → Claude 의견과 종합을 거쳐 댓글 1개를 남깁니다. 댓글에는 가치·규모(스텝 수)·위험·추천(지금/나중/보류)과 같은 점·다른 점이 들어갑니다.
- 본문을 고치면 의견을 다시 냅니다. Codex를 못 쓸 때는 "Codex 의견 대기"로 표시합니다. Codex가 다시 되면 Actions → `idea-review` → Run workflow(해당 Issue 번호)로 채웁니다.
- 의견만 내고 코드는 바꾸지 않습니다. 하기로 정하면 PM이 계획 Issue로 옮깁니다.
- 상황판 PM 브리핑 탭의 '아이디어함'에서 일자·항목·내 의견·종합 의견을 봅니다. 프로젝트가 여러 개면 위 칩으로 걸러 봅니다.
- 관리자 로그인에서는 '아이디어 적기'(항목 80자 + 내 의견 4000자)로 바로 등록합니다. 등록 후 1~3분 뒤 의견이 붙습니다. 서버 쓰기 토큰(`ORCH_GITHUB_TOKEN`)이 필요합니다.
